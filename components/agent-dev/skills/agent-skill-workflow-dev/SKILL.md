# agent-skill-workflow-dev · Agent/Skill/Workflow 开发规范与自查

三类资产、一个核心纪律：**通用件写通用，场景差异走输入**。

- **agent（子代理）**：一份定义文档（角色 + 输入 → 判定/执行 → 输出契约），被主代理启动，执行一批同类任务。
- **skill（技能文档）**：教主代理"何时做、做什么"的触发式说明书。
- **workflow（编排层）**：主代理协调代码与子代理的流程定义——形式不限（声明式配置、代码、框架 DSL、对话流程均可），本技能只约束其中与 agent 交互的通用原则，不绑定任何编排格式。

## P0 — 通用件纪律（本技能的立身之本）

> 根因模式：一个判定型子代理的定义文档里写死"本代理可能被场景 A 或场景 B 调用，
> 两者共用同一判定、判定完各自去做 X/Y"——把**编排层的调用场景**（谁在调、什么时机、
> 拿结果做什么）焊进了**判定件**的角色定义。后果：新增第三个调用场景必须改 agent
> 定义；不改则 agent 对新场景一无所知或行为错误。这就是"通用件被特化"。

1. **判断件只认输入，不认调用方**。子代理、判定模板、worker 脚本这类会被多处复用的件，
   其定义文档**只能描述**："给定什么输入（数据/参数/路径）→ 做什么判定 → 输出什么"。
   **禁止**写入：本件被哪些场景谁调用、调用方拿结果去做什么、场景之间如何分工。
   这些是编排层知识，归编排定义或调用方代码的注释。
2. **场景差异 = 输入差异**。多场景复用同一通用件时，差异只允许出现在：
   - 输入载体的**数据内容**（同一模板，不同数据值）；
   - 队列名/目录名/路由键等**寻址参数**（由编排侧传给通用件）；
   - 结果的**消费方式**（由调用方按输出契约自取自用）。
   **禁止**为每个场景复制一份通用件，或在通用件里写 if-场景分支。
3. **场景说明降位**。通用件文档确需提示"输入可能来自多个调用方"时，只写**一行中性
   多态说明**（如"调用参数给出输入来源，取到即执行"），**禁止**展开解释各场景的业务
   含义、时机、产物去向——那是调用方自己的文档。
4. **归一判据**：要写第二份相似定义/模板前，先问"能不能是同一份 + 不同输入"——
   答案几乎总是能。判定语义同构（A 与 B 是否同一问题）就共用定义；编排语义（判完
   删候选还是删待办、要不要重排序号）就分家。定义共用"怎么判"，调用方各自管
   "判完怎么用"。

## P1 — LLM 交互契约（大模型是不稳定的）

1. **信号通道唯一且严格**。给 LLM 看的输出（stdout/消息）必须真实打印且及时；
   实现日志、访问日志、内部进度**禁止**混入。宁可少打印，不可多打印——多余信息
   诱导 LLM 猜想、"帮程序判断"。
2. **健壮性问题代码自己解决**。端口冲突、重试、资源清理、幂等——全部进代码内部。
   **禁止**在技能/指令文档里教 LLM"如何判断端口冲突""如何兜底"。
   给 LLM 的命令**必须极简无参数**：一条命令 + 明确结束信号。
3. **指令只写"做什么"，不写"为什么/怎么做"**。技能与指令文档只含：执行的动作 +
   可感知的明确信号（结束标志逐字引用程序真实输出）。产品背景、内部机制、
   实现步骤全部不写。自检法：指令内容放进代码注释也合理 = 泄露实现，移除。
4. **指称直接用业务名**。指令与模板中的指称必须直接使用输入字段/槽位的业务名
   （如"待判意见"），**禁止**引入 A/B、甲乙、source/target 代称再解释映射——
   那是两次无谓翻译。
5. **判断收敛进代码，LLM 只做语义判定**。代码能端到端完成的逻辑（检查→映射→提交），
   **禁止**拆成"检查 → LLM 决策 → 执行"多步。调用链尽量直接，LLM 中间决策环节
   越少越稳。
6. **结论止于事实**。判定类子代理输出布尔/枚举结论与理由，**禁止**在角色定义/输出
   契约里写"判定为 X → 就不采纳"这类下游决策——采纳与否由调用方按结论自行决定。

## P2 — 定义与接线（编排接入纪律）

1. **定义与接线同步**。新组件（子代理/技能/脚本）落地时必须同步接入其调用入口
   （编排声明、注册表、路由、技能索引——按所在平台形态）。只改定义不改接线 =
   不可达 = 没接入执行路径。反向同理：删组件必须删全部接线。
2. **任务数据走输入载体，不走定义**。任务级数据通过输入载体（模板渲染的提示、
   消息体、参数、数据文件）传入子代理；agent 定义文档零任务数据。编排侧负责
   "生成输入 → 启动子代理 → 收集输出 → 按场景消费"。
3. **产物隔离**。不同调用方/不同轮次的输出产物必须物理隔离（独立目录或命名前缀），
   按前缀扫描的收集逻辑才不会互吃对方的产物。共用判定内核（P0）≠ 共用产物落点。

## P3 — 代码纪律（实现层）

1. **独立模块判据**：≥2 个调用方才独立成文件；≤10 行且单调用方必须内联。
2. **禁止不可达防御**：写校验/外层 except 前，枚举被调函数全部可能返回——子集校验、
   内层已全 catch 的外层 except 都是死分支，删除。
3. **禁止无调用方的功能分支**：加分支/模式参数前确认存在调用方传入；无接线即无调用方。
4. **资源获取一次**：凭证/配置/连接在同一执行内获取一次向下传递，禁止各子函数重复获取。
5. **DRY 收敛**：同一逻辑样板散落 ≥3 个文件，必须提取装饰器/公共函数收敛单点。
6. **私有符号禁止跨模块导入**：A 模块 import B 模块的下划线名，说明这批符号该搬去
   公共模块公开命名——跨模块私有导入即抽公共模块的信号。
7. **并行产物幂等**：多实例并行写产物时，消费侧消费完即删（幂等），防重复消费
   与序号复读误删。
8. **每状态独立输出路径**：正常/早退/异常禁止共用固定文案；输出前自检文案与状态一致。

## 模式一：开发（新做或改造）

按顺序走，每步有硬性产出：

1. **定性**：这是判断件（会被多场景复用）还是编排件（单场景流程）？
   判断件 → 按 P0 设计输入接口；编排件 → 按 P2 接线。
2. **设计输入**：列出通用件需要的全部输入（数据/参数/路径），确认全部从调用方传入
   （输入载体、命令行参数、路由参数），通用件定义里零场景数据。
3. **写子代理定义**：元数据（name/description 必需，其余按平台惯例）+ 核心职责一句话 +
   执行流程（取任务 → 逐个执行 → 按输出契约写结果 → 结束）+ 判定标准 + 输出 schema。
   判定标准写"什么算真"的判据（如"修复同一根因即同类"），不写场景。
4. **写判定模板**：槽位即业务名，中性措辞，角色只描述判定本身。
5. **写编排脚本**：生成输入 + 启动子代理 + 收集输出 + 场景特定的消费逻辑
   （删什么、怎么重排、记什么账）。
6. **接线**：把新组件登记进其调用入口；给主代理的指令只写"运行此程序 → 按输出
   启动子代理 → 等全部完成"级别的任务描述，程序输出契约逐字段解释
   （LLM 要读的字段才解释）。
7. **验证**：全量测试 + 离线端到端冒烟（stub 掉外部依赖，验证输入生成、结果收集、
   槽位填充正确）。

## 模式二：自查（审既有资产）

逐条过下列清单，任一命中即记 finding（级别：架构 / 契约 / 死代码）：

1. [ ] 通用件定义里出现具体调用场景（场景清单 + 各自业务含义/时机/产物去向）→ **架构**：场景知识降位到编排层。
2. [ ] 同一判定逻辑存在 ≥2 份定义/模板/函数（含仅注释不同的复制品）→ **架构**：归一为一份 + 输入差异。
3. [ ] 通用件里有 if-场景分支或按调用方名字改变的输出 → **架构**：拆输入参数。
4. [ ] 跨模块 import 下划线私有名 → **架构**：抽公共模块公开命名。
5. [ ] 指令/技能文档写了实现步骤、内部机制、端口/进程细节 → **契约**：删至动作 + 信号。
6. [ ] 指令用 A/B/甲乙代称再解释映射 → **契约**：换业务名。
7. [ ] 判定输出契约/角色里写了下游决策（"→ 不采纳"）→ **契约**：删，结论止于事实。
8. [ ] 给 LLM 的输出通道混入实现日志（端口/路径/访问/进度）→ **契约**：静默或降为文件日志。
9. [ ] LLM 中间决策环节可由代码端到端替代 → **契约**：合并步骤。
10. [ ] 分支/模式/参数无调用方传入（全库检索零调用）→ **死代码**：删。
11. [ ] 互相引用成环、无编排入口的整链模块 → **死代码**：整链删（git 历史可回溯）。
12. [ ] 文档/注释描述的用法与实际调用不符（参数不存在、路径不可达）→ **死代码**：改文档对齐现实。
13. [ ] 不同调用方的输出产物同目录同前缀（收集侧会互吃）→ **架构**：物理隔离。
14. [ ] 防御分支不可达（枚举返回值与校验集合求交集）/ 外层 catch 死分支 → **死代码**：删。

自查产出格式：finding 列表（文件:行 + 级别 + 一句话根因 + 处置建议），**不直接动手改**——
交用户裁决后再进入模式一执行改造。

## 反模式（见即纠）

- "为了两种场景写两个 agent/两份模板" —— 先问输入差异能不能覆盖。
- "在子代理定义里解释编排层的流程分工" —— 降位，那是编排层的事。
- "程序不稳定？在指令里教 LLM 兜底" —— 兜底进代码，指令保持极简。
- "判定模板顺便写上判定后怎么处理" —— 越权，调用方自治。
- "加个以防万一的校验分支" —— 先证明它可达。
- "改了组件忘了接线" —— 等于没接入（定义与接线同步）。
- "把具体编排格式（某框架的配置结构、字段名）当通用概念写进规范" —— 通用原则不绑定框架形态。
