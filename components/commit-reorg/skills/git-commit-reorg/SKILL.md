# Git Commit Reorg · 提交历史重排

将杂乱、巨大或逻辑混乱的提交历史重构为一组独立、原子、逻辑清晰且逐提交可编译通过的高质量提交序列。

## 一、铁律与触发纪律

1. **显式触发**：仅在用户明确提出“整理提交历史”、“拆分提交”、“重排提交”时触发；严禁在常规开发或普通功能合并中擅自重写提交历史。
2. **Plan-First 门禁**：在动手执行任何 Git 重写操作前，必须向用户呈现完整方案，包括：
   - 现状梳理（分支、base、当前提交列表与 diff 统计）；
   - 目标提交序列（每步提交的意图、改动范围、预估行数预算）；
   - 拆分与切片方法；
   - 备份与归档方案；
   - 验证方案与风险提示。
   **只有获得用户明确许可后方可进入执行阶段。**
3. **双备份 + 物理归档**：
   - Git 引用双备份：在重写前建立 `git branch backup/reorg-<name>-<timestamp>` 与 `git tag pre-reorg-<name>-<timestamp>`，并立即验证两个引用严格指向当前 HEAD（前缀固定为 `backup/reorg-`，避免与 gwf sync 的分支备份冲突）。
   - 仓库外物理归档：使用 `git format-patch <base>..HEAD -o <archive_dir>` 及 `git diff <base>..HEAD > <archive_dir>/full.patch` 物理归档至仓库外安全目录，防止工作树丢失。
4. **单提交预算约束**：
   - 以 `git diff <base>..HEAD --numstat` 最终态全量改动为基准。
   - 单个提交新增行数（+行）严格控制在 **≤ 900 行**（纯自动生成代码或锁定文件需单独声明提交）。
5. **终态树逐字节等价**：
   - 重排完成后，必须执行 `git diff <backup_ref> HEAD`，输出必须**严格为空**，证明重排不增删改任何最终代码。
6. **交付与安全回退纪律**：
   - 备份资产（分支、tag、patch 归档目录）必须保留至用户确认验收后才允许手工清理，绝不自动删除。
   - 重排结果在未 push 到远端前，可通过 `git reset --hard <backup_ref>` 瞬时整体安全回退。
## 二、切片与构造方法

1. **基底软重置**：
   - 获取公共祖先 `git merge-base <target_base> HEAD`。
   - 执行 `git reset --soft <base>`，将全部改动保留在暂存区/工作区。
2. **切片构造与行号基准**：
   - **行号基准**：中间版切片一律以最终文件的 1-based 行号为绝对基准；若用 `sed -n 'A,Bp' file | cat -n` 核对边界，原行号换算为 `A + 输出行号 - 1`。
   - 依赖关系前置：先基础设施/公共类型/抽象层，后业务逻辑/上层调用，最后测试与文档。
   - 构造原则：基于最终文件的 1-based 行号自底向上构造，替换必须是整块 `(start, end)`。
   - 多态中间态与提交间工作区纪律：
     - 每提交完一个切片，必须将工作区文件恢复为最终版（保证工作区基准始终为最终态，留给后续提交切片）。
     - 多提交共用文件（如同一模块分别归属 C2/C4/C6）的中间版归属顺序必须自洽：某代码块若在 C5 才引入，C2 版必须剥除、C5 版再加回，绝不在早期提交中引用尚不存在的符号或函数。
3. **逐提交验证阶梯**：
   - 行数预算验证：每次提交后执行 `git show --stat HEAD`，检查新增行数是否超标（+行 ≤900）。
   - 语法与静态检查：根据项目语言执行最小完整检查。
     - Python：不仅做 `py_compile`（抓不到函数内逻辑/名称错误），更要用 `importlib.util.spec_from_file_location` 实际加载模块抓模块级未定义符号，并借助 AST 遍历函数内引用的下划线私有符号/局部符号是否已被定义。
     - Node：执行 `node --check` 校验语法。
   - 符号残留扫描：执行正则/grep 检查中间提交中是否存在引用了后续提交才引入的新模块或未定义符号。
   - 测试通过性：中间提交若包含测试用例，必须保证当期提交用例全部 PASS。
4. **提交信息规范**：
   - 沿用仓库既有前缀与风格（例如 `feat:`、`fix:` 或项目约定前缀如 `【代码检视】`）。
   - 每个提交表达一个完整且内聚的功能增量，Commit Message 正文列出涉及的文件与核心变动要点。
## 三、Windows / MSYS 实战陷阱防范

1. **路径双轨制**：
   - Windows 下 MSYS/Git Bash 的 `/tmp/` 映射物理路径常与 Windows 原生环境不一致。
   - 物理归档目录应使用 `os.path.expanduser("~")` 或绝对 Windows 盘符路径（如 `%TEMP%`）。
2. **中文提交消息与管道**：
   - 避免使用 `git commit -m "$(cat << 'EOF' ...)"` 在某些终端导致的 UTF-8 解码错乱。
   - 优先通过临时文件 `git commit -F <msg_file>` 写入多行或带中文的 Commit Message。
3. **Grep 子串误报**：
   - 校验符号残留时警惕子串包含误报（例如检索 `import re` 可能会误匹配 `from refresh_cache import ...`）。
   - 正则匹配必须加词边界 `\b`。
4. **MSYS 命令混用**：
   - 避免把 MSYS `find`/`xargs` 与 Windows 原生工具（如 `cmd.exe` / `powershell`）混合链式管道传参，防止斜杠路径转义崩溃。
